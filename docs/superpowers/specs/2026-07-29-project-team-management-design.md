# 员工群组与项目组管理设计

日期：2026-07-29

## 1. 背景与目标

当前系统已经提供员工账号、单一群组和项目可见性管理，但 `users.group_id` 只能表达“一名员工属于一个群组”，并且“同组”权限通过项目创建者与访问者是否属于同一群组判断。这无法准确支持跨部门项目，也混淆了长期组织关系与临时项目协作关系。

本次改造将“员工群组”和“项目组”拆成两个独立概念：

- 员工群组表示长期、相对固定的组织或专业团队，例如研发组、设计组、测试组。一名员工可以属于一个或多个员工群组。
- 项目组表示围绕单个项目建立的动态协作团队。项目创建后自动拥有项目组，项目创建者自动成为项目负责人；项目组可以吸收来自不同员工群组的成员。

目标如下：

1. 支持管理员创建、修改和删除员工群组，并为员工分配多个员工群组。
2. 允许所有启用的员工账号创建项目，而不是仅限系统管理员。
3. 项目创建者自动成为项目负责人，并能维护当前项目的项目成员和角色。
4. 支持跨员工群组选择项目成员，也支持按员工群组批量选择当前成员。
5. 系统管理员可以管理所有项目；项目负责人和项目管理员管理各自项目；普通项目成员不能修改项目组。
6. 平滑迁移现有单群组数据，不破坏已有账号、项目、任务、会话和访问控制数据。

## 2. 概念边界

### 2.1 员工群组

员工群组属于系统级长期组织结构：

- 由系统管理员创建、重命名、删除和维护成员。
- 一名员工可以属于多个员工群组。
- 保留“默认组”，未明确分组的启用员工至少属于默认组。
- 员工群组只用于组织、筛选和批量选择，不直接等同于项目权限。
- 员工调组不会自动把他加入或移出既有项目组，避免组织调整意外改变活跃项目权限。

### 2.2 项目组

项目组属于单个项目的动态协作范围：

- 每个项目第一版只对应一个统一项目组，不再创建同名的全局员工群组。
- 创建项目时自动建立项目组成员关系，创建者自动成为项目负责人。
- 项目负责人和项目管理员可以添加、移除项目成员及修改成员角色。
- 系统管理员拥有所有项目的兜底管理权限，但无需成为每个项目的显式成员。
- 项目成员可以来自任意员工群组，不受项目创建者所属员工群组限制。
- 一个员工可以同时参加多个项目组。
- 项目归档后保留项目成员关系和历史审计，不允许普通协作变更；恢复项目后继续使用原项目组。

### 2.3 按员工群组批量添加

项目组中的“添加整个员工群组”是批量选择操作，而不是永久动态绑定：

- 操作时把该员工群组当前启用成员加入项目组。
- 员工群组后续新增员工不会自动获得旧项目权限。
- 员工以后离开长期员工群组，也不会自动退出已经参与的项目。
- 管理者可以在确认界面取消个别员工后再提交。

此规则避免新入职或调组员工意外看到旧项目及历史会话。

## 3. 数据模型

### 3.1 员工与员工群组多对多关系

保留 `user_groups` 表作为员工群组定义，新增关联表：

```sql
CREATE TABLE user_group_memberships (
  user_id TEXT NOT NULL,
  group_id TEXT NOT NULL,
  is_primary INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  created_by TEXT,
  PRIMARY KEY (user_id, group_id),
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (group_id) REFERENCES user_groups(id) ON DELETE CASCADE
);
```

约束与规则：

- 同一员工和群组只能有一条成员关系。
- `is_primary` 用于界面优先展示，可选；权限判断不只检查主群组。
- 每名启用员工至少有一个员工群组；移除最后一个群组时自动加入默认组。
- 被软删除员工的关联关系保留，恢复账号时继续保留；如无任何关联则加入默认组。
- 现有 `users.group_id` 在兼容期保留并映射为主群组，所有新逻辑以关联表为准。待调用方全部迁移后再单独规划删除旧列，不在本次范围内直接删除。

### 3.2 项目组成员关系

新增项目成员表：

```sql
CREATE TABLE project_memberships (
  project_id TEXT NOT NULL,
  user_id TEXT NOT NULL,
  role TEXT NOT NULL,
  created_at TEXT NOT NULL,
  created_by TEXT,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (project_id, user_id),
  FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE CASCADE,
  FOREIGN KEY (user_id) REFERENCES users(id)
);
```

`role` 支持四级项目角色：

| 角色 | 标识 | 能力 |
|---|---|---|
| 项目负责人 | `owner` | 管理项目、项目组、角色、任务与会话；项目必须至少有一名负责人 |
| 项目管理员 | `manager` | 管理成员、任务和会话；不能移除最后一名负责人 |
| 项目成员 | `member` | 查看项目、创建和处理任务、按项目设置启动会话 |
| 项目访客 | `viewer` | 只读查看有权访问的项目内容 |

规则：

- 项目创建事务中同步插入创建者的 `owner` 关系。
- 一个员工在一个项目只有一个最终角色，不产生重复项目成员。
- 项目负责人可以把其他成员提升为负责人，再移交自己的负责人身份。
- 禁止删除或降级项目最后一名负责人。
- 员工账号软删除后，历史项目成员记录保留，但不再计入可选成员和有效权限。

## 4. 权限模型

### 4.1 系统级权限

| 操作 | 系统管理员 | 普通员工 |
|---|---:|---:|
| 创建项目 | 允许 | 允许 |
| 创建、编辑员工群组 | 允许 | 禁止 |
| 调整员工的长期群组 | 允许 | 禁止 |
| 查看全部员工及其长期群组 | 允许 | 仅在项目选人器中查看必要的启用员工信息 |
| 兜底管理任意项目 | 允许 | 禁止 |

### 4.2 项目级权限

| 操作 | 系统管理员 | 负责人 | 项目管理员 | 项目成员 | 项目访客 |
|---|---:|---:|---:|---:|---:|
| 查看项目 | 允许 | 允许 | 允许 | 允许 | 允许 |
| 修改项目基本信息 | 允许 | 允许 | 允许 | 禁止 | 禁止 |
| 添加、移除项目成员 | 允许 | 允许 | 允许 | 禁止 | 禁止 |
| 修改项目成员角色 | 允许 | 允许 | 允许，但不能管理负责人 | 禁止 | 禁止 |
| 删除或归档项目 | 允许 | 允许 | 默认禁止 | 禁止 | 禁止 |
| 创建任务 | 允许 | 允许 | 允许 | 由项目现有开关控制 | 禁止 |
| 启动会话 | 允许 | 允许 | 允许 | 由项目现有开关控制 | 禁止 |

系统现有 `visibility`、`allow_user_ids`、`allow_group_ids` 仍可用于公开、私有、允许名单等资源级访问策略，但项目成员关系成为项目协作权限的主要来源。访问控制的优先级为：

1. 系统管理员；
2. 有效项目成员角色；
3. 项目或子资源的显式允许名单；
4. 公开可见策略；
5. 默认拒绝。

现有“同组可见”语义改为兼容模式：读取旧数据时可继续生效，新建或编辑项目时界面引导使用项目成员，不再用项目创建者的单一员工群组隐式代表整个项目团队。

## 5. 后端接口设计

### 5.1 员工群组接口

沿用 `/api/admin/user-groups` 的创建、列表、更新、删除接口，扩展返回成员统计和成员摘要。

新增或调整：

- `GET /api/admin/users`：员工返回 `group_ids`、`groups` 和可选 `primary_group_id`，兼容返回旧 `group_id`、`group_name`。
- `PUT /api/admin/users/:id/groups`：一次性替换员工的全部长期群组，服务端保证至少一个有效群组。
- 创建单个或批量员工时接受 `group_ids`；旧 `group_id`、`group_name` 请求仍兼容并转换为单元素集合。
- 删除员工群组时，如果仍有启用员工成员关系则拒绝；管理员需先迁移成员，默认组永远不可删除。

### 5.2 项目组接口

新增：

- `GET /api/projects/:projectId/members`：列出项目成员、项目角色和员工群组摘要。
- `POST /api/projects/:projectId/members`：添加一个或多个员工，支持统一角色或逐人角色。
- `PATCH /api/projects/:projectId/members/:userId`：修改项目角色。
- `DELETE /api/projects/:projectId/members/:userId`：移除项目成员，校验最后一名负责人。
- `POST /api/projects/:projectId/members/from-group`：读取某员工群组当前启用成员并批量加入；请求中允许提交最终选中的用户 ID，避免不可控的隐式全量添加。

所有写接口统一执行：登录校验、项目管理权限校验、员工启用状态校验、重复关系幂等处理和管理员审计记录。

## 6. 前端交互设计

### 6.1 管理中心：员工群组

现有“群组管理”改名为“员工群组”，说明文字明确其为长期组织关系。

- 群组卡片展示群组名称、启用员工数和全部历史记录数。
- 点击群组卡片可打开成员管理弹窗，搜索并多选员工。
- 员工列表中的单选群组下拉改为多选标签控件。
- 新增员工表单支持选择多个员工群组，默认选择“默认组”。
- 批量新增格式允许群组字段使用 `|` 分隔多个群组，例如 `研发组|AI 技术组`；不存在的群组是否自动创建沿用当前管理员批量新增行为。
- 移除员工最后一个群组时，前端提示并由后端自动回到默认组。

### 6.2 创建项目

所有启用员工继续可以创建项目。

- 创建者无需先选择成员即可提交。
- 项目创建成功后，创建者自动成为负责人。
- 创建成功页或项目首页显示“邀请成员”快捷入口，但不把邀请作为创建项目的阻塞步骤。

### 6.3 项目设置：项目组

项目设置新增“项目组”区域：

- 顶部展示负责人、项目管理员、项目成员和访客数量。
- 支持按姓名、账号和长期员工群组搜索员工。
- 支持逐人添加，也支持选择一个员工群组后勾选其当前成员批量添加。
- 已加入成员列表展示头像/名称、账号、长期员工群组标签、项目角色和加入时间。
- 负责人和项目管理员可在行内调整角色或移除成员。
- 当前操作者不能导致项目失去最后一名负责人。
- 系统管理员进入任意项目时可执行兜底管理，界面标明“系统管理员权限”，避免误以为自己是项目成员。

响应式布局中，桌面端使用表格或双栏选择器，窄屏改为成员卡片；所有关键操作保留文字标签，不只依赖图标。

## 7. 数据迁移与兼容

迁移步骤必须幂等：

1. 创建 `user_group_memberships` 和 `project_memberships` 表及索引。
2. 把每个现有用户的 `users.group_id` 写入员工群组关联表；空值或无效值写入默认组。
3. 把每个现有项目的 `created_by` 写为该项目的 `owner`。
4. 保留 `users.group_id`、`group_name` 等旧字段和接口响应，兼容尚未改造的登录、上下文和权限调用方。
5. 新写入员工群组时同步维护旧 `users.group_id` 为主群组，直到所有调用方切换为多群组查询。
6. 不根据旧“同组可见”自动把整个员工群组写入所有历史项目，避免突然扩大历史项目权限。

迁移应在事务中运行，并通过唯一键保证重复启动不会生成重复关系。

## 8. 错误处理和审计

用户可见错误使用明确中文文案：

- 员工群组不存在或已删除。
- 只能选择启用的员工账号。
- 你没有管理该项目组的权限。
- 项目必须至少保留一名负责人。
- 默认组不能删除。
- 只能删除没有启用员工的空员工群组。
- 批量添加中部分员工已经在项目组，系统将其视为成功并跳过重复添加。

项目成员新增、移除、角色变更，以及员工长期群组变更均写入现有管理员/系统审计机制，记录操作者、目标项目或员工、变更前后值和时间。

## 9. 测试与验收

### 9.1 数据层与接口测试

- 一名员工可以加入多个员工群组，重复加入保持幂等。
- 移除最后一个长期群组后自动进入默认组。
- 项目创建者在同一事务中成为项目负责人。
- 普通员工可以创建项目并管理自己创建项目的成员。
- 普通项目成员不能修改项目组。
- 项目管理员可以管理普通成员，但不能移除或降级最后一名负责人。
- 系统管理员可以管理任意项目。
- 按员工群组批量添加只复制提交时选中的当前成员，后续员工群组变化不自动修改项目组。
- 软删除员工立即失去有效项目访问权，历史成员关系保留。
- 旧 `group_id` 数据能正确迁移，迁移重复运行不产生重复记录。

### 9.2 前端测试

- 员工多群组选择、保存、刷新后保持一致。
- 创建、重命名和删除空员工群组行为正确。
- 项目设置能搜索不同员工群组的员工并添加到同一项目。
- 按群组批量选择时可取消个别成员。
- 角色调整、移除成员和最后负责人保护有清晰反馈。
- 普通成员看不到项目组管理按钮。
- 桌面端和窄屏布局无溢出，键盘可访问，加载与错误状态明确。

### 9.3 回归验证

- 登录和用户恢复逻辑不受多群组迁移影响。
- 现有项目、任务、研究、会话读取权限保持可用。
- 项目创建、项目设置保存、任务创建和会话启动流程通过。
- 前端生产构建通过，后端修改文件通过语法或类型检查。

## 10. 非本次范围

- 一个项目内再拆分多个研发、设计、测试子项目组。
- 员工群组的层级树、部门负责人、成本中心等完整组织架构。
- 员工群组与项目组的实时自动同步。
- 外部访客邀请、邮件邀请和单点登录目录同步。
- 删除旧 `users.group_id` 列及所有兼容字段。

这些能力可在真实使用反馈证明有必要后单独设计，避免第一版过度复杂。
