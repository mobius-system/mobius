## 2. 为什么慢、为什么不能搜多个词

### 已由源码确认

- 每次查询重新读取候选会话的 primary JSONL 和旧 sidecar；先做原始行匹配，再解析和抽取展示文本。无持久化正文倒排索引。
- `buildMatcher` 将整个 `q` 当一个子串，或转义成一个正则。因此 `API repair` 查的是带空格的连续字符串，不是分别包含两个词。
- 默认候选 200 个，最大 600 个，按会话活跃时间排序；**不等于全部历史可搜索**。候选上限发生在权限过滤前，也可能挤掉较旧的可读会话。
- 有 8 路并发、450ms 防抖、AbortController 和 SSE；这些已经存在，不能作为根本提速方案重复建议。
- 全局预算 120 秒，只在领取下一个会话前检查；单次 `scanSession` 文件循环未接收截止时间或取消信号。一次大文件扫描可跨过预算，客户端取消也不保证扫描及时停止。
- 原始行预匹配再对抽取文本匹配，两者表示不同，JSON 转义等情况存在漏检风险；抽取文本还有约 200KiB 上限，长消息尾部可能漏检。
- 当前时间范围按会话 `last_active`，并非按命中消息的时间。

### 结论

问题是**查询时扫描历史文件**，而不是按钮或 loading 样式。成熟路径是：**写入时/后台增量建索引，查询时查倒排索引**。SSE 只能改善等待感；增加扫描并发、缓存少数热词或缩小默认范围都不能解决根因。

## 3. 技术选型

| 方案 | 适用条件 | 本项目取舍 |
| --- | --- | --- |
| SQLite FTS5 | 单机部署、希望少一个服务、索引可本地持久化 | **首选验证**；项目已用 better-sqlite3 + WAL，但必须验证部署包的 FTS5/tokenizer 能力 |
| Meilisearch / Typesense | 产品化站内搜索，需要开箱即用的联想、筛选、容错 | 备选；引入独立服务，需实测中文、代码标识符、多词与短语语义，不能假定与现状等价 |
| OpenSearch / Elasticsearch | 多节点、大规模日志、复杂分析器与权限过滤 | 规模验证需要时再用；当前直接上集群运维成本偏高 |
| Tantivy | 希望嵌入式检索但可接受 Rust 服务/原生集成 | 能力成熟，Node 项目集成维护成本高于 FTS5 |
| 向量数据库 / RAG | 自然语言语义召回 | 不作为本次主链路；不能替代错误码、文件名、代码片段的确定性查询 |

**建议：独立 SQLite 搜索库 + FTS5 + 独立索引进程/检索 worker。** 不把大批回填、同步 FTS 查询放进 HTTP 主事件循环，也不把索引写放进业务主库的事务。

选型门禁：先测真实语料、磁盘预算和并发，达不到第 10 节目标再比较独立搜索服务。不能仅凭“百万条”预言是否需要迁移；单条消息大小和候选命中率同样重要。

## 4. 检索语义：先定义，再选 tokenizer

### 默认行为

- 空格分隔多个条件，默认 **全部包含 AND**；提供“任一包含 OR”切换。
- 默认要求同一条消息同时满足条件，不把不同会话拼在一起。后续如支持“同一会话的不同消息分别满足”，必须单独命名，展示各词证据，不与默认语义混用。
- 保留当前子串体验；引号内内容是连续短语，`-词` 为排除条件。首版不承诺括号和任意布尔表达式。
- 不自动删掉常见词；`in`、`ERR`、`C++`、路径和错误码在代码场景都有意义。
- 单字条件首版不开放；每个正向条件至少 2 个字符。只有排除词的查询拒绝执行。后续单字需求必须有专门成本评估。

| 输入 | 期望 |
| --- | --- |
| `API repair` | 同一消息中分别包含 API 与 repair，顺序不限 |
| `报错 修复` | 同一消息中分别包含两个中文条件，不能要求连续出现 |
| `"Connection lost" tokenproxy` | 同一消息含连续短语及 tokenproxy |
| `API -timeout` | 包含 API 且不包含 timeout |
| `repair.md MODEL_PROVIDER_RANK_OVERRIDE` | 标点、下划线视作查询内容，不误当引擎语法 |

通过一个共享的查询解析规范生成 AST，后端编译为安全的检索条件；**不把用户原文直接当 FTS MATCH 表达式**。SQL 参数绑定防 SQL 注入，FTS 语法转义/白名单负责另一层安全，两者不可相互替代。限制总长、条件数、候选验证数和执行时间；语法错误就近提示，不静默换成另一种查询。

### 中文与代码子串

FTS5 默认 unicode61 **不会自动完成符合预期的中文分词**，不能直接建表就宣布支持中文多关键词。

建议先验证以下两路召回，均在候选消息上用统一匹配器做精确确认：

1. **长度 ≥3 的条件：trigram 索引。** 对规范化文本做三字符倒排召回，适配中文连续文本、文件名和代码子串。引号、符号和 Unicode 行为必须用部署版本实测；必要时由编译器生成安全 gram 条件，而不是透传 MATCH。
2. **两字符条件：辅助 bigram 索引。** 对同一规范化正文生成相邻字符对，编码为安全 ASCII token 后写入辅助 FTS 表。两字符条件查该表；长短条件混合时以消息/块标识求交或求并。FTS5 trigram 对少于三个字符的 MATCH 不能满足原有两字符入口，不允许暗中回落全库 LIKE。

两路只是候选召回；最终 AND/OR、短语、排除、大小写、W 都在完整候选消息上判定。大小写敏感使用折叠索引召回超集，再验证原文；查询与索引必须使用一致的 Unicode 规范化策略。用原文重新定位高亮，不拿规范化后的字符偏移直接切原文。

`W` 首期明确沿用现有 `[A-Za-z0-9_]` 边界定义，中文不宣传“语言学全词匹配”。如果以后改为分词边界，需要显式交互与兼容性说明。

bigram 索引有额外磁盘/写入成本，应列入基准测试。语言分词 + 词级 BM25 可作为后续相关性增强，不应先改变现有子串语义。

## 5. 架构与数据

```text
各模型会话历史 / primary + 旧 sidecar / 可用的规范化历史事件
              ↓ 适配、去重、隐藏自动注入上下文
独立 indexer → search.sqlite（正文 + trigram + bigram + checkpoint）
                                  ↑
SearchModal → 查询 AST → 检索 worker → 当前权限验证 → 片段/会话聚合
                                  ↓
                       限量分页结果、覆盖率与耗时
```

### 数据边界

- JSONL/各 backend 的完整历史接口继续作为权威源，索引是可删除重建的派生数据。不能改为仅索引 `messages_v2`：现有后端说明 assistant/tool/thinking 并未完整落该表。
- 为每种 backend 明确来源适配器与能力矩阵；找不到路径应计入 `unavailable`，不是“已索引但无结果”。远端历史只有接口可读取时才能回填，不假定宿主可访问所有文件。
- 索引库放在持久化数据目录，由宿主索引服务拥有，不把宿主路径塞给不可见的沙箱。新部署必须检查目录挂载、权限和剩余磁盘。
- `documents`：稳定消息键、session/project/scope、role、消息时间、原始可搜索文本、内容 hash、来源标识、提取器版本；不信任索引中的 owner 字段作为权限真相。
- `chunks`：超长消息分块建索引，记录 message_id、块序号、原文区间；不沿用 200KiB 截断。块间保留覆盖最大可接受短语长度的重叠，且短语长度有明确上限。
- 同一消息的 AND 条件即便分别位于不同块，也须在 message_id 级求交；短语做原文跨块确认；排除条件按整条消息判断，不能只看某个正向命中块。
- `checkpoints`：来源路径/身份、文件 generation、已提交 byte offset、尾部未完成行、mtime/大小、最后成功时间、解析失败数。
- `index_state`：schema/tokenizer/extractor 版本、索引 generation、回填状态、可索引来源总数、已完成数和积压量。

### 清洗与定位

- 抽取用户、助手、工具输入/输出等可见内容，复用并补齐现有各 backend 的解析规则，不索引 JSON 包装字段冒充可见正文。
- 自动注入的项目/用户上下文遵守 `search-content.ts` 的排除规则，同时保留标题之后的真实问题。清洗后插入硬边界或拆段，防止删除区两侧被拼接为虚假短语。
- primary/sidecar 优先用稳定消息 ID 去重，无 ID 时采用来源身份、位置和内容指纹组合；不能仅用片段前 60 字去重。
- 搜索结果保留消息 uuid/id、时间和来源位置供跳转；仅有时间兜底时要允许“定位到附近”，不宣称精确命中。

## 6. 增量索引与生命周期

1. 历史回填按项目分批，优先活跃会话；限速、可中断、持久化进度，不在服务启动时同步扫完。
2. 新数据先用增量尾读落地；文件事件只作提示，低频校验大小/身份作补偿。后续有可靠规范化消息事件时，改为事件驱动 + 补偿扫描。
3. 按字节 offset 续读，保留半条 JSON/UTF-8 边界；只有完整记录、索引和 checkpoint 同一事务提交成功才推进，崩溃后幂等重放。
4. 检测 truncate、替换、轮转、模型切换、路径迁移；generation 变化后重建对应来源并清理旧记录。mtime 不能单独作为可靠水位。
5. 删除项目/会话、文件移除和保留期清理须有 tombstone 或对账任务同步删除；权限撤销立即由请求时鉴权生效，不等待索引刷新。
6. tokenizer/提取规则升级写入新 generation，回填验证后原子切换；旧 generation 延迟回收。索引目录含敏感正文，应限制访问并遵守原文的删除/备份策略。

## 7. 查询执行、权限与一致性

1. 鉴权、解析 AST，校验 project/session 范围。
2. 生成当前用户可读范围，结合项目/会话过滤参与候选召回；若现有复杂 JS 权限不能完全下推，则分批召回、批量调用现有权限逻辑并继续补足，而不是固定取全局 TopK 再过滤一次。
3. 在 worker 中对 gram 候选做 message 级集合运算和原文确认。拒绝无法有效收窄的大范围查询，返回“请增加条件”，不能无限枚举后伪装成无结果。
4. 最终发出每个片段前用当前业务数据执行 `canReadSession` 及对应父级权限约束。索引里的元数据可能过期，不能绕过现有可读性口径。
5. 按 session 聚合，每组显示有限证据；默认相关性排序，以满足条件数、短语命中、文本位置/密度等可解释信号为主，活跃时间仅作次级排序。不能把 gram 的 BM25 直接宣传为词级相关性；保留“最近活跃”排序选项。
6. 游标绑定 query_hash、排序键、索引 generation、用户/权限版本，避免翻页重复、跨条件复用。权限变化时失效并重验；不暴露未授权的计数、分面或覆盖率。

默认时间筛选先保留“会话最近活跃时间”语义，并在控件提示中写明；按消息时间查找应是明确新增的筛选项，而非偷偷改变“7天内”的含义。

每请求使用可真正中断的 worker 查询预算；候选验证循环持续检查 deadline/取消。对无法协作中断的同步 SQLite 查询，需要使用驱动可验证的 interrupt 机制或隔离/终止对应 worker，不能只设 Promise 超时。HTTP 断连事件按实际 Node 生命周期验证，不机械复用现有 `req.close`。读写连接分离、WAL、短事务，并监控 checkpoint、索引合并和回填对查询的影响。

## 8. API 与元素 1 的交互设计

### API 草案（非已实现）

新增版本化端点 `/api/search/v2`，避免旧调用方的“整句子串”被静默改为 AND：

```json
{
  "q": "API repair",
  "operator": "and",
  "project_id": "13cb82f2",
  "range": "7d",
  "time_field": "session_last_active",
  "case_sensitive": false,
  "whole_word": false,
  "sort": "relevance",
  "limit": 30,
  "cursor": null
}
```

响应包含 `items`、`next_cursor`、`took_ms`、`index_generation`、`index_lag_ms`、`coverage`、`partial`、`partial_reason` 和结构化命中区间。统计只针对当前用户可见范围；coverage 区分完整、回填中、不可用，不能声称覆盖全部历史。搜索词不写入普通访问日志；如采用 GET，需额外配置日志脱敏。

首屏结果足够快时普通 JSON 即可；保留 SSE 兼容通道不影响架构。流式进度用于解释回填/受限状态，不作为加速本身。

### 原浮层的拟议变化

```text
范围 [pawbench] [全部项目]           [标题与描述] [会话全文]
[ 搜索内容：API repair                                 ]
[全部包含 ▾] [近7天活跃 ▾] [相关性 ▾]        [Aa] [W]
多个关键词用空格分隔 · "双引号" 搜短语 · -词 排除
─────────────────────────────────────────────────────
结果（按会话分组）               128 ms · 索引已更新
项目 › 任务 › 会话
用户  … API … repair …           查看命中消息
```

- 保持现有 680px 浮层、项目范围、键盘导航和结果跳转，先不重做视觉风格；此处只是文字线框，未写 HTML 原型。
- 将“深度搜索”命名为“会话全文”，减少“必然很慢”的暗示；“快速搜索”对应“标题与描述”。如果入口较多，应统一术语，而非只改这个组件。
- AND/OR 用“全部包含/任一包含”，不要求普通用户理解布尔运算。折叠帮助提供短语、排除词例子；Aa/W 有可访问名称和具体语义说明。
- 防抖建议 200–300ms，Enter 立即提交；输入更新立即使旧请求失效，取消浏览器请求与后端查询两端工作。
- 已有结果在新查询时保留但明确标成旧结果/更新中，避免闪空；不能让旧结果冒充当前查询。结果为空、查询过宽、语法错误、权限不足、索引回填中、服务故障是不同状态。
- 显示“索引回填中：当前可搜索范围 …”，允许用户主动选择受限历史扫描；**不自动回退到原来的两分钟扫描**。该维护模式需独立限流与可取消能力。

## 9. 分阶段落地与回滚

### P0：验证，不替换

核对部署环境 FTS5/trigram、持久化路径和各 backend 数据可见性；用脱敏真实语料验证两字符、中文、代码及跨块匹配。采集当前首结果耗时、总耗时、扫描字节数、取消延迟和漏检案例，建立基线。

### P1：后台索引 + 影子查询

新增独立搜索库、来源适配器、回填器和 v2 查询；仍保留旧入口。用显式全文参考匹配器评估 AND/OR/短语正确性，不能把旧版截断扫描结果当完整真值。影子流量需限额，不让双查把线上负载翻倍。

### P2：小范围启用

仅对覆盖率达标的项目/用户启用新链路，加入多词控件、片段高亮和覆盖率提示；按权限测试、性能和召回门禁逐步扩大。全文与元数据先共享查询语义规范，不强求首版合并所有搜索接口。

### 回滚

Feature flag 恢复旧版入口并停止回填，不动 JSONL 和业务库；界面清楚提示旧版单词/整句语义和扫描限制。旧版的多词输入不能悄悄变成另一种含义。新索引可以重建，版本切换失败可恢复上一 generation。

## 10. 验收与观测

以下均为建议目标，先固定硬件、磁盘、语料大小、平均/最大消息长度和并发，再出报告：

| 维度 | 门禁 |
| --- | --- |
| 热索引查询 | 在约定代表性语料与 10 并发下，首屏端到端 P95 ≤500ms，P99 ≤1.5s；另报检索纯耗时 |
| 冷缓存 / 常见词 / 无命中 | 单独报告，不拿热词均值掩盖长尾；有确定截止时间与明确 partial_reason |
| 新消息可搜索 | 稳态 P95 ≤5s；持续观察 backlog 与最大滞后，而非只看平均值 |
| 取消 | 断开或改词后，旧查询工作通常在 500ms 内停止；验证后端实际 CPU/I/O，不只验证 UI |
| 正确性 | 固定夹具中英文、多词 AND/OR、短语、排除、大小写、W、JSON 转义、两字符均符合定义 |
| 完整性 | 覆盖老会话、不在前 600 的会话、长消息尾部、多块 AND、跨块短语、sidecar 重复与所有支持的 backend |
| 权限 | 跨用户、共享/撤销、父任务权限、会话删除、缓存和分页计数不泄漏 |
| 生命周期 | 半行追加、UTF-8 边界、轮转、截断、崩溃重启、版本重建和删除对账不丢不重 |
| 运维 | 记录库体积/原文体积比、写放大、回填速度、磁盘余量、worker CPU/RSS、WAL 大小和 HTTP 事件循环延迟 |

日志只记录 request_id、条件数、范围、耗时、验证候选数、返回数、取消/超时原因与索引滞后；正文、密钥和原始搜索词默认不记。缓存首版可以不做；若引入，必须包含用户、权限版本、query AST、范围和索引 generation，并在权限变化后失效。

**本次建议决策：先验证独立 SQLite FTS5 的 trigram + 两字符辅助索引方案；优先交付多词语义与可靠增量索引，不先上向量检索或大集群。**
