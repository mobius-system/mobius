01发布链路与职责

① 源码与版本mobius/desktop/package.json
electron/ · src/
② 平台安装包build.py:build_electron
electron-builder.yml
③ GitHub Releasemobius/apps-release.json
.github/workflows/apps-release.yml
④ 站内下载backend/services/sync-desktop-builds.js

Electron 主进程、预加载脚本和登录页编译到 app.asar；Python 通过 extraResources 随安装包分发。工作台页面由服务器提供。发布壳代码需要新安装包；更新工作台页面走服务器部署。

本机 / 单站点

build.py 编译后将安装包复制到 mobius/desktop-builds/ 并生成本地清单，本站即可提供文件下载。

统一 Release / 多站点

apps-release.yml 下载已构建文件并核验，上传到 GitHub；各服务器从统一 Release 同步。桌面版、Android 和 iOS 链接共同写入发布清单。

02选定版本并编译

所有平台使用同一源码提交。确定新版本 V 后，同步更新桌面端 package.json 与 package-lock.json，通过 PR 合入 GitHub main；从该合并提交构建。下例中的版本和标签均为示例，执行前替换为本次选定值。

# 在发布分支更新版本；依赖安装与外网下载使用专用 tmux 窗口
V=0.3.76
npm --prefix mobius/desktop version "$V" --no-git-tag-version
npm ci --prefix mobius/desktop
npm run build --prefix mobius/desktop
node mobius/desktop/tests/aimux-lifecycle.test.cjs
npm run test:aimux --prefix mobius/tui
目标构建位置命令（项目根目录）分发格式
Windows x64当前 Linux 构建机可交叉打包python3 build.py --build-electron --targets win-x64ZIP
macOS Apple Silicon具备签名和公证凭据的 macOSpython3 build.py --build-electron --targets mac-arm64DMG + ZIP
macOS Intel具备签名和公证凭据的 macOSpython3 build.py --build-electron --targets mac-x64DMG + ZIP

各目标顺序构建，或在独立 checkout 中构建：它们共用 resources/python/。已有匹配架构的 resources/python-<target>/ 时可加 --skip-fetch-python。在隔离的发布工作区执行构建，再将验收通过的产物交给分发目录。

构建产物、日志和网络约定
原始安装包  mobius/desktop/release/Mobius Desktop-V-win-x64.zip
分发安装包  mobius/desktop-builds/mobius-desktop-V-win-x64.zip
本地清单    mobius/desktop-builds/manifest.json
打包日志    /tmp/mobius-eb-win-x64.log

依赖和 Python 首次下载放在新建 tmux 窗口中执行；外网下载低于 500 KB/s 时使用 proxychains 命令 重试。代理通过命令包装配置。build.py 直接调用 electron-vite，所以发布前单独执行上面的 npm run build 完成 TypeScript 检查。

03验收与签名

通用运行验收

解压或安装本次产物，验证登录、工作台、AIMUX 在线、关闭后重新开启、退出后 watchdog 回收，并保留状态面板截图。检查包内版本及 Python 架构与目标一致。

python3 scripts/desktop_manifest.py validate \
  --dir mobius/desktop-builds

macOS 独立验收

使用 Developer ID Application 签名与 Apple 公证。每种架构构建后，立即对该目标的输出目录运行校验脚本；六项检查通过后再进入公开分发。

bash scripts/verify-mac-build.sh "$V" arm64 \
  mobius/desktop/release/mac-arm64
# Intel：目标目录通常为 release/mac，arch 参数为 x64

Mac 检查覆盖签名完整性、签名身份及 Team、Gatekeeper、公证票据、主程序架构、内置 Python 架构与启动。按实际输出目录传参，确保目录中只有本次目标应用。

签名凭据配置位置

构建机或 CI 密钥存储提供 CSC_LINK、CSC_KEY_PASSWORD。公证可使用 APPLE_ID + APPLE_APP_SPECIFIC_PASSWORD，或 APPLE_API_KEY + APPLE_API_KEY_ID + APPLE_API_ISSUER。具体 Team 和 entitlements 以 mobius/desktop/electron-builder.yml 为准。文档与发布日志只记录检查结果。

04准备清单并发布

先上传验收后的安装包，取得 GitHub runner 可访问的下载地址。 然后更新 mobius/apps-release.json：设置新 releaseTag（以 apps-v 开头）、标题、desktop.version，逐个登记 platform / arch / format / file / url / size / sha256。每个 URL 必须返回对应文件的真实内容。

统一流程也读取 mobile 和 ios。本次只升级桌面端时，可保留经复核仍可下载的移动端文件与 TestFlight 链接。只发布 Windows 时，桌面清单列本次 Windows 文件；发布完整桌面版时，收齐同版本五个文件：Windows ZIP 与两种 Mac 架构的 DMG、ZIP。

发布前离线优先校验
# 使用新的输出目录；本地缺少的文件会按配置 URL 下载
python3 scripts/prepare-apps-release.py \
  --config mobius/apps-release.json \
  --output /tmp/mobius-release-check-NEW \
  --source-dir mobius/desktop-builds \
  --source-dir mobius/mobile-builds
cd /tmp/mobius-release-check-NEW
sha256sum -c SHA256SUMS.txt

准备脚本只检查配置所列文件的字节数与 SHA-256。发布人同时复核桌面清单版本、文件名、平台覆盖范围与包内版本。脚本生成 apps-manifest.json、desktop-manifest.json、mobile-manifest.json、校验文件及发布说明。

将最终发布清单通过 PR 合入 main。确认 main 的发布标签与清单完全一致后，选择一种触发方式：

# 方式 A：在已核验的合并提交上打标签；推送 tag 触发发布
RELEASE_TAG=apps-v2026.11.01
RELEASE_COMMIT=REPLACE_WITH_REVIEWED_MERGE_SHA
git tag "$RELEASE_TAG" "$RELEASE_COMMIT"
git push origin "refs/tags/$RELEASE_TAG"

# 方式 B：手动运行当前分支上的工作流，按配置中的 tag 发布
gh workflow run apps-release.yml -R mobius-system/mobius \
  --ref main -f draft=false
gh run list -R mobius-system/mobius --workflow apps-release.yml --limit 5
gh run watch RUN_ID -R mobius-system/mobius --exit-status

GitHub 仓库须已启用该工作流，且清单引用的下载源可被 runner 访问。工作流使用 GITHUB_TOKEN 的 contents:write 权限；源码进入 main 走 PR，发布命令只推送已核验的 tag。

05分发、核验与回退

GitHub Release 发布后，配置了 DESKTOP_WEBHOOK_URL 与 DESKTOP_WEBHOOK_TOKEN 的工作流会请求 POST /api/webhook/desktop-sync。服务器也会在启动约 30 秒后检查，随后默认每 60 分钟检查一次；间隔由 MOBIUS_DESKTOP_SYNC_INTERVAL_MIN 控制。

同步服务优先选择公开的 apps-v* Release，下载桌面文件，将 desktop-manifest.json 保存为本地 manifest.json。用户下载界面从这个清单显示可用平台。

gh release view "$RELEASE_TAG" -R mobius-system/mobius \
  --json url,isDraft,assets

SITE=https://YOUR_MOBIUS_SITE
curl -fsS "$SITE/desktop-builds/manifest.json"
curl -fI "$SITE/desktop-builds/mobius-desktop-$V-win-x64.zip"
# 完整下载后再核对 SHA-256；下载操作放在专用 tmux 窗口
发布完成的证据

工作流成功；Release 标签、版本、文件集合正确；每个分发站点的清单和安装包一致；完整下载文件的哈希匹配；Windows / macOS 对应目标的真实启动验收通过。记录源码 SHA、构建平台、签名结果、Release 地址和校验值。

回退采用新的 apps-v* 发布标签，清单明确指向已验收的旧版本安装包。这样服务器按相同流程同步，历史版本和校验记录也能继续追踪。仅修改本机清单时，应同时考虑下一次自动同步的覆盖行为。

服务器源码变动按项目约定先 commit，再执行 python3 start.py --detach。安装包目录由静态路由提供；安装在用户电脑上的 Electron 通过新包安装或受控替换 app.asar 生效。

附录 · 当前仓库边界与排错

症状 / 现状原因处理
触发 CI 后没有编译新代码当前只有统一发布工作流，下载并校验预构建文件。先在构建机产出包，再更新 apps-release.json。源码注释提到的 desktop-release.yml 当前不存在。
直接运行工作流会发旧包当前 apps-release.json 仍为 apps-v2026.09.19、桌面 0.0.30；源码 package.json 已是 0.3.75。发布前更新并复核清单；本文未修改发布配置、创建标签或触发 Release。
macOS 打包成功但用户打不开签名 / 公证凭据缺失时打包器可能仍以 0 退出；build.py 没有自动调用独立验收脚本。Mac 构建在隔离目录进行，执行 verify-mac-build.sh，确认通过后再公开文件。开发模式包不进入正式分发。
Windows 显示未知发布者当前配置 signAndEditExecutable:false，生成未签名 ZIP。当前流程按未签名包交付；如需签名版，另配 Windows 签名环境与发布验证。
同版本新包下载到旧内容同名覆盖遇到缓存；同步器按文件大小跳过已有包。发布新版本和唯一文件名，核对完整下载 SHA-256。当前 JS 同步器并未自动复验 SHA-256。
旧同步脚本拒绝 apps-v 标签scripts/sync-desktop-builds.py 只接受 desktop-v。统一发布使用后端 JS 同步服务或 webhook；旧 Python 脚本用于旧标签兼容路径。
draft=true 没有保护已有 Release工作流只有创建分支读取 draft；已有标签会执行 upload --clobber 和 edit --latest。使用全新标签建立草稿，在发布前核实该标签不存在。已有草稿转公开应显式发布并复核。
Webhook 返回 200 但文件不齐同步结果可能含 failed；请求 body 中 tag 不用于固定同步目标。检查返回 JSON、实际选择的公开 Release、每个站点的清单和文件；等待结果全部通过。
